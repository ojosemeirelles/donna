# Shadow Sessions Architecture — DONNA-004

## Overview

Extends the Shadow Army system (DONNA-002) from **prompt-level hints** to **real agent delegation**. Each shadow gets a dedicated session backed by the Pi embedded runner, enabling autonomous task execution with persona-specific system prompts, isolated conversation history, and execution tracking.

## Current State (DONNA-002)

```
User message → classifyIntent() → orchestrate()
  → injects hint into parent system prompt
  → same session handles everything
```

Shadows are announced but never actually execute. The parent session's AI model sees the hint and roleplays the shadow persona — no isolation, no dedicated tools, no execution history.

## Target State (DONNA-004)

```
User message → classifyIntent() → orchestrate()
  → ShadowSessionManager.dispatch()
    → resolve or create shadow session (child)
    → inject SOUL.md as system prompt
    → run via Pi embedded runner
    → stream result back to parent channel
    → track in execution history
```

### Session Identity

Shadow sessions use a deterministic ID scheme:

```
shadow:{shadowName}:{parentSessionId}
```

Examples:
- `shadow:tusk:telegram-12345` — Tusk researching for Telegram user 12345
- `shadow:beru:discord-67890` — Beru executing for Discord user 67890

This ensures:
- One shadow session per shadow per parent session (reuse across messages)
- Easy lookup and cleanup
- Clear parent-child relationship

### SessionEntry Extensions

Leverage the existing `spawnedBy` and `spawnDepth` fields in `SessionEntry`:

```typescript
type ShadowSessionMeta = {
  shadowName: string;        // "Tusk", "Beru", etc.
  shadowIntent: ShadowIntent; // "research", "exec", etc.
  parentSessionId: string;
  createdAt: number;
  lastActiveAt: number;
  executionCount: number;
};
```

Stored in the session store alongside regular sessions. The `spawnedBy` field links to the parent. `spawnDepth = 1` marks it as a shadow sub-session.

### System Prompt Construction

Each shadow session gets a system prompt built from:

1. **SOUL.md** — Shadow persona from `~/.donna/shadows/{name}/SOUL.md` (generated by extractor)
2. **Tool restrictions** — Only the tools listed in `ShadowDefinition.tools`
3. **Parent context** — Channel info, user preferences, conversation summary
4. **Execution boundary** — Max tokens, timeout, delegation rules

```typescript
function buildShadowSystemPrompt(
  shadow: ShadowDefinition,
  soulMd: string,
  parentContext: ParentContext,
): string {
  return [
    `# ${shadow.name} — ${shadow.role}`,
    "",
    soulMd,
    "",
    "## Restrictions",
    `- Tools: ${shadow.tools.join(", ")}`,
    `- Respond in the user's language`,
    `- Do NOT delegate to other shadows`,
    `- Max response: concise, actionable`,
    "",
    "## Context from Monarch session",
    `- Channel: ${parentContext.channel}`,
    `- User: ${parentContext.userId}`,
    parentContext.summary ? `- Summary: ${parentContext.summary}` : "",
  ]
    .filter(Boolean)
    .join("\n");
}
```

### Dispatch Flow

```typescript
async function dispatch(
  message: string,
  shadow: ShadowDefinition,
  parentSession: SessionEntry,
  deliveryContext: DeliveryContext,
): Promise<ShadowDispatchResult> {
  // 1. Get or create shadow session
  const sessionId = `shadow:${shadow.name.toLowerCase()}:${parentSession.sessionId}`;
  const shadowSession = await getOrCreateSession(sessionId, shadow, parentSession);

  // 2. Build system prompt from SOUL.md
  const soulMd = await loadSoulMd(shadow.name);
  const systemPrompt = buildShadowSystemPrompt(shadow, soulMd, {
    channel: parentSession.chatType,
    userId: parentSession.sessionId,
    summary: null, // future: compact parent transcript
  });

  // 3. Run via Pi embedded runner
  const result = await runEmbeddedPiAgent({
    sessionId,
    body: message,
    systemPrompt,
    deliveryContext,
    // Inherit model/auth from parent
    modelOverride: parentSession.modelOverride,
    authProfile: parentSession.authProfile,
  });

  // 4. Track execution
  await tracker.record({
    shadowName: shadow.name,
    intent: classifyIntent(message),
    parentSessionId: parentSession.sessionId,
    startedAt: Date.now(),
    durationMs: result.durationMs,
    tokenUsage: result.usage,
    status: result.error ? "failed" : "completed",
  });

  return {
    response: result.response,
    shadowName: shadow.name,
    sessionId,
  };
}
```

### Execution History

Stored at `~/.donna/shadows/history.jsonl` (append-only JSONL):

```typescript
type ShadowExecution = {
  id: string;               // ulid
  shadowName: string;
  intent: ShadowIntent;
  parentSessionId: string;
  startedAt: number;
  durationMs: number;
  tokenUsage: { input: number; output: number };
  status: "completed" | "failed" | "aborted";
  error?: string;
};
```

Queryable via `/shadow-history` or `/status` command.

### Session Lifecycle

```
Created         → on first delegation to a shadow for a parent session
Active          → while Pi embedded runner is processing
Idle            → waiting for next message (session file persists)
Pruned          → after 24h idle (configurable via DONNA_SHADOW_SESSION_TTL_MS)
```

Pruning reuses the existing `store-maintenance.ts` logic with a shadow-specific TTL.

### Execution Limits

| Limit | Default | Config Key |
|-------|---------|------------|
| Max concurrent shadow sessions per parent | 2 | `shadow.maxConcurrent` |
| Shadow session idle TTL | 24h | `shadow.sessionTtlMs` |
| Max execution time per dispatch | 120s | `shadow.execTimeoutMs` |
| Max token budget per dispatch | 4096 output | `shadow.maxOutputTokens` |
| Execution history retention | 7 days | `shadow.historyRetentionDays` |

### Error Handling

Shadow delegation errors are **non-fatal** (same as current design):

```typescript
try {
  const shadowResponse = await shadowSessionManager.dispatch(...);
  return shadowResponse;
} catch (error) {
  log.warn("Shadow delegation failed, falling back to parent session", { error });
  // Fall back: inject hint into parent prompt (DONNA-002 behavior)
  extraSystemPromptParts.push(`[Shadow Army] ${shadow.name} attempted but failed...`);
  // Continue with normal parent session flow
}
```

### Igris (Orchestrator) — Special Case

Igris handles "complex" intents and can **sub-delegate** to other shadows:

```
User → Igris (complex task)
  → Igris decomposes into sub-tasks
  → Igris dispatches to Tusk (research) + Iron (write)
  → Igris aggregates results
  → Returns to user
```

This is Phase 2 (T3+). For T2, Igris runs as a single shadow session like the others. Sub-delegation is future work tracked separately.

## Decisions

1. **Reuse Pi embedded runner** — No new execution engine. Shadow sessions are regular Pi sessions with shadow-specific system prompts and spawn metadata.

2. **Deterministic session IDs** — `shadow:{name}:{parentId}` enables session reuse across messages and simple cleanup.

3. **Graceful fallback** — If shadow dispatch fails, fall back to DONNA-002 hint injection. Never break the parent session.

4. **SOUL.md as system prompt** — Shadows get their persona from the already-generated SOUL.md files, not hardcoded strings.

5. **JSONL history** — Append-only, simple, grep-friendly. No database needed for shadow execution tracking.

6. **Igris sub-delegation deferred** — Complex orchestration is out of scope for initial implementation. Igris runs as a flat shadow first.
